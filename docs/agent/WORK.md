# AI作業フロー

この文書は、複雑な変更、Child分割、統合の時だけ参照する。日常の小変更では `AGENTS.md` と対象コードだけで進める。

## 1. 作業を分ける基準

次のどれかに当てはまる時だけChildへ分割する。

- 単独で価値を提供し、独立して検証できる。
- API、DB、UIなど変更境界や依存関係が明確に異なる。
- 並行作業または別レビューにより待ち時間・リスクを実際に減らせる。
- 失敗時に他の変更から切り離して戻す必要がある。

ファイル数や作業時間だけでは分割しない。小さな修正を階層化してbranch・MD・mergeを増やさない。

## 2. RouterとChildの所有情報

親Routerは次だけを保持する。

| 項目 | 内容 |
|---|---|
| Child | 機能名とbranch |
| 状態 | 未着手 / 作業中 / Child検証済み / 統合済み |
| 契約 | 親や他Childへ提供するAPI・schema・状態・UI境界 |
| 依存 | 先に必要な変更、共有ファイル、migration順 |
| 統合条件 | 接続点と親で確認する振る舞い |

Child文書は、長時間作業・再開・引継ぎに必要な場合だけ作る。最低限、目的、範囲外、base、変更境界、重要判断、完了条件、検証結果、残存リスクを持つ。親と同じ説明を複製しない。

## 3. Child完了時の引継ぎ

統合前に次を確認する。

- 親の基準commitとChild head
- 変更ファイルと意図しない差分の有無
- 公開API、型、DB schema・migration、認証・権限、共有状態への影響
- 実行した検証コマンドと結果
- 未実行項目、環境制約、既知の残存リスク
- 統合後に初めて成立する接続テスト

commit SHAだけを引継ぎにしない。SHAは変更の所在を示すが、契約と検証証拠の代わりにはならない。

## 4. 統合手順

1. 最新の親とcleanな作業状態を確認する。
2. Childが想定したbaseからの差分と、親側でその後変わった共有境界を比較する。
3. Childを1つ統合し、競合がなくてもAPI・型・schema・権限・状態管理の接続点を確認する。
4. 変更に近いテストを実行し、次に親の主要フローと必要な全体検証へ広げる。
5. 接続不良を確定仕様内で直し、同じ検証を再実行する。
6. 最終diff・status・検証証拠を確認してからRouterを `統合済み` に更新する。
7. 次のChildは、前Childの統合結果が安定してから統合する。

専用integration branchは、競合解消、複数Childの組合せ確認、migration・認証・共有型など高リスク境界の隔離に使う。不要なら親へ直接fast-forwardまたは通常mergeする。

## 5. 検証の選び方

| 変更 | 最初の検証 | 統合時に追加する検証 |
|---|---|---|
| 局所ロジック | 対象unit/feature test | 呼出元と主要回帰 |
| API・型 | backend contract + frontend変換 | 実際の要求/応答フロー |
| DB・migration | migrationとデータ条件 | fresh/upgrade経路、関連API |
| 認証・権限 | 許可と拒否の両方 | UI表示と直接APIアクセス |
| UI状態・DnD | component/store test | ブラウザー主要フロー |
| 文書のみ | diff、リンク、整合性 | アプリテスト不要 |

全suite・build・ブラウザー確認は、共有境界、統合、release前、または局所検証だけでは回帰を捉えにくい場合に実行する。実行できない検証を別の検証で隠さない。

## 6. 質問と承認境界

次の手順が要求された結果に向かい、可逆で既存設計の範囲内なら続行する。小さな実装選択、テスト追加、明らかな回帰修正は質問しない。

ユーザー判断が必要なのは、製品動作の選択、主要設計の変更、範囲拡張、データ損失の可能性、production・外部変更、他者の作業を上書きする危険がある場合である。質問時は観察した事実、各選択肢の影響、推奨案を1つ示す。

## 7. 維持管理

AGENTS改善は、実際に繰り返した失敗や摩擦から始める。新しい規則を追加する前に次を順に確認する。

1. 既存規則の明確化または削除で解決できるか。
2. テスト・lint・scriptで機械的に強制する方が適切か。
3. 全作業に適用されるか。そうでなければ関連文書やツールに置けるか。
4. 追加するcontextコストより予防効果が大きいか。

候補変更は別review branchで比較し、承認前にmainへ反映せず、進行中作業へ遡及適用しない。
