# AGENTS v2.1 — 独立再レビュー報告

基準: `docs/agents-v2` / `be26cb1300ba274370513226c4ac53cf4bd1e610`
候補: `review/agents-v21-handoff-evidence-20261007`

## 結論
v2.1は新規作業で試用できる水準だが、そのまま最終版にするより、停止条件・引継ぎ・文書義務を調整した本候補を推奨する。大きな構造変更ではなくv2.x内の改善である。実運用の効果は未測定。

## 維持するもの
必要時だけ責任を分割し、下位から上位へ統合する。最小文脈から必要な依存先を調査する。無関係なdirty状態は保護して継続する。統合後の接続点・親範囲の回帰を確認し、未検証を完成と書かない。特定製品・IDE・単一の強いAI・常時フルテストを前提にしない。

## 変更と理由
| 対象 | 調整 | 理由 |
| --- | --- | --- |
| 小判断 | 「一意」を外し、承認済み仕様・契約内の小さく可逆な選択を許す | 複数案だけで止まる余地をなくす。可逆でも新仕様・UXは承認対象 |
| 承認境界 | 未承認の変更だけ確認し、既存承認を再利用する | すでに依頼されたAPI実装等を再承認させない |
| Child handoff | 検証したコードSHA、コマンド/環境/結果、制約/未検証を一緒に残す | SHAは内容の識別であり、何を検証したかの証明ではない |
| 親状態 | 採用Child SHAと統合後に検証したコードSHAを区別する | Childテストと組み立て後のテストを混同しない |
| 未検証 | 担当環境で実行できない検証を明示して引き継ぐ | 携帯・対話・無料AIでも作業を担当できる。必要な検証の完了を偽らない |
| 検証順序 | 最も近い意味のある検証から影響に応じて広げる | 毎回全検査は不要だが、単体成功で接続・回帰検証を省かない |
| 文書 | MANUALを必要時だけ作成し、進捗の重複を省く | 各Childで2文書を作る義務と読める部分を解消する |
| 競合 | 承認済み統合で意図が明確な競合だけ自律解消する | 明白な接続修正との矛盾をなくす。他者の変更を捨てる判断は確認する |
| 優先順位 | 上位指示・ユーザー指示の下でAGENTSを適用する | 「全AI作業に優先」という過大な表現を修正する |

追加意見の「残る制約」と「近いテストから」は採用した。ただし項目を増やすためではなく既存の引継ぎ・検証文を置換した。制約の列挙だけで必要な完了条件を免除せず、近いテストだけで親統合を完了させない。

## 分解・統合・SHAの扱い
親が責任と契約を分け、下位の結果を依存関係順に上位へ戻す。「逆順」は独立した兄弟を作成日時の逆順でmergeする意味ではない。契約変更時は影響する担当と親検証を見直す。

Childは同じ作業MD内に短く検証情報を残す。専用台帳や固定テンプレートは不要。親は採用SHAだけでなく実際の差分と組み合わせを確認する。文書のみの追記commitと検証したコードcommitが異なる場合は、どのコードを検証したかを明記する。SHAを文書自身に埋め込む再commitループは不要。

AIの実行能力不足は未検証の引継ぎとして扱い、未検証を成功と代筆しない。統合担当が必要な実行環境と検証を確保する。この役割分担はIDEや特定agent機能を必要としない。

## 手動で照合したケース
以下は文書の机上確認であり、モデル実行試験ではない。

| ケース | 規則上の判断 |
| --- | --- |
| 同じ契約を満たす小実装が2通り | 自律選択。方法の数だけでは質問しない |
| 新しいUX案が可逆 | 承認範囲外なら確認する |
| ユーザーが公開API変更をすでに依頼 | 同じ変更を再承認させない |
| 無関係な他作業のdirty | 保護して継続する |
| 所有者不明の重なる変更 | 上書きせず確認する |
| 承認されたmergeの明白な接続競合 | 契約内で解消し再検証する |
| ChildのSHAだけ渡された | コマンド・環境・結果・制約を確認する |
| CPython合格、実機なし | 実機未検証を引き継ぎ、必要な親完了条件は残す |
| 複数Childが単体合格 | 統合したコードで接続点・親回帰を確認する |
| 統合検証後にコードが変わる | 影響する検証を再実行し検証SHAを更新する |
| 変更なしで同じ検査を繰り返す | 未解決の懸念がなければ省く |
| 小さな内部修正、利用手順なし | 作業MDと完了報告で足り、MANUALを新設しない |

## 検証と制限
文書差分と内容の整合性を確認する範囲の変更。アプリコード・設定・テストは変更しない。アプリテスト、実際の弱いモデルでの遵守率、無人実行や本番統合での効果は未検証。専用CI・署名証明・固定上限など未発生問題への対策は追加しない。

原本ブランチとmainを変更せず独立候補をcommit/pushする。正式採用はユーザー判断とし、現在進行中のTicketには遡及適用しない。
