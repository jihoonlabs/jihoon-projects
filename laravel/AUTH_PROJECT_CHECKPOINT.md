# 인증 프로젝트 체크포인트

최종 갱신: 2026-09-15  
현재 브랜치: `feature/auth-login`  
코드 기준 커밋: `e2cbcc2`  
현재 상태: 이메일·Google·LINE 인증 흐름 구현 및 검증 완료

## 1. 프로젝트 목표

Next.js App Router와 Laravel을 사용해 실제 서비스에 재사용할 수 있는 인증 기반을 만든다.

- Laravel Sanctum SPA 세션 인증
- 이메일·비밀번호 로그인
- Google·LINE 소셜 로그인
- 계정 상태에 따른 접근 제어
- 인증 정책을 Feature Test로 검증
- 공개 GitHub 포트폴리오 수준으로 정리

## 2. 인증 방식과 계정 정책

사용자는 다음 세 가지 방법 중 하나를 선택해 로그인한다.

- 이메일과 비밀번호
- Google
- LINE

각 로그인 방식은 자동으로 서로 연결하지 않는다.

- 동일 이메일이어도 기존 계정과 자동 연결하지 않음
- 소셜 계정은 `provider`와 `provider_user_id`로 식별
- provider 이메일은 `provider_email`에 참고 정보로 저장
- 신규 소셜 사용자의 `email`과 `password`는 `null` 허용
- 로그인할 때는 가입 시 사용한 인증 방법을 사용

## 3. 완료된 기능

### 일반 인증

- 회원가입
- 비밀번호 확인 입력
- 로그인과 로그아웃
- `/api/auth/me`를 이용한 세션 복원
- 비로그인 사용자의 보호 API 접근 시 `401`
- 로그인과 회원가입 Rate Limit
- 비밀번호 최소 길이와 영문·숫자 정책

### 이메일 인증

- `User` 모델에 `MustVerifyEmail` 적용
- 회원가입 시 인증메일 발송
- 회원가입 직후 자동 로그인하지 않음
- 미인증 사용자의 이메일 로그인 차단
- 미인증 로그인 시 `403 email_not_verified` 반환
- 미인증 로그인 세션 제거
- 서명된 URL을 이용한 이메일 인증
- 잘못된 이메일 해시 차단
- 만료된 인증 URL 차단
- 인증 완료 후 `/login?verified=1` 이동
- 인증메일 재전송 API
- 미등록·인증 완료 이메일에는 실제 알림을 발송하지 않음
- 외부 응답을 동일하게 유지하여 계정 존재 여부 보호
- 인증메일 재전송 Rate Limit

### 계정 상태

- 신규 사용자의 기본 상태는 `active`
- `suspended` 사용자의 일반·소셜 로그인 차단
- 로그인 후 정지된 사용자의 보호 API 접근 시 `403`
- 정지 사용자 발견 시 인증 세션 무효화
- 이후 요청은 미인증 상태로 `401`
- `active.user` 미들웨어를 보호 API에 적용

### 소셜 로그인

- Google Socialite 로그인
- LINE Socialite 로그인
- Google·LINE 실제 브라우저 로그인 확인
- 기존 SocialAccount 재로그인 시 중복 생성 방지
- OAuth 실패 처리와 내부 예외 기록
- User와 SocialAccount 생성을 DB 트랜잭션으로 처리
- 로그인 후 세션 재생성과 `/tickets` 이동

### Next.js

- 로그인 화면
- 회원가입 화면
- 비밀번호 확인 검증
- 로그인과 회원가입 화면 간 이동
- 회원가입 완료 안내
- 이메일 인증 완료 안내
- 소셜 로그인 오류 안내
- 미인증 로그인 오류 구분
- 인증메일 재전송 버튼과 성공·실패 처리
- URL 메시지 표시 후 쿼리 파라미터 제거
- React Effect 내부의 불필요한 상태 변경 제거

- 인증메일 재전송
- Laravel 로그의 새 서명 URL 생성

- 인증 완료 메시지
- 인증 후 이메일·비밀번호 로그인
- Google·LINE 로그인

자동 테스트에서는 실제 외부 OAuth 서버나 메일 서버에 접속하지 않는다.

- Socialite 사용자 응답은 mock 사용
- 이메일 Notification은 fake 사용
- OAuth와 이메일 링크 동작은 브라우저에서 별도 확인
- 개발 환경의 인증메일은 `MAIL_MAILER=log`로 확인

## 7. 이후 서비스 구조

인증 이후 업무 데이터는 다음 구조를 기준으로 한다.

- Company 개념은 사용하지 않음
- Project가 최상위 업무 단위
- Project 아래에 Team 구성
- 한 사용자는 여러 Project와 Team에 소속 가능
- Ticket은 Project에 필수 소속
- Ticket의 Team과 담당자는 선택적으로 지정

## 8. 작업 규칙

- 기능을 한 단계씩 구현하고 결과를 확인한다.
- 코드 변경 전 목적과 보안 정책을 먼저 확인한다.
- 한 번에 여러 오류를 수정하지 않는다.
- lint 오류는 숨기지 않고 원인을 수정한다.
- 변경 후 오류가 늘면 해당 변경만 되돌리고 다시 확인한다.
- 자동 테스트와 실제 브라우저 확인을 구분한다.
- 완료된 기능은 오류 재현이나 정책 변경이 없으면 다시 구현하지 않는다.
- 로그인 기능 완성 후 파일별로 필요한 이정표 주석을 검토한다.
- 전체 테스트, lint, build, `git diff --check`, push 완료 지점을 공식 체크포인트로 삼는다.
